# Native hashes: the `speedupy-native` package

Decision D3 of `RETROFIT.md`, taken by the maintainers on 2026-11-19. This
document is the design that the package follows and that Task 25 consumes.
The package is created under issue #106 in the organization's account; this
page is updated when the first release is on PyPI.

## Why a separate package

SpeeduPy offers six hashes: `md5` (standard library), `murmur` (`mmh3`) and
`xxhash` (`xxhash`), which install from wheels on every platform, and three
native ones, `a5hash`, `meowhash` and `museair`, which today are compiled by
hand into `.so` files that the code loads by file name through `ctypes`. That
works on one Linux machine and nowhere else: the files are not versioned, the
sources are in three other repositories, and `.so` is not how Windows (`.dll`)
or macOS (`.dylib`) name a shared library.

The decision is that all six hashes come with `pip install speedupy` on Linux,
Windows and macOS, with no compiler on the user's machine. A Python extension
with prebuilt wheels is the standard way to do that. Keeping it in its own
package, instead of inside `speedupy`, keeps `speedupy` pure Python (a plain
`pip install -e .`, a two-minute CI, a simpler tool paper), gives the native
code its own release cycle, and lets a wheel be rebuilt for a new Python or a
new system without touching `speedupy`.

## The sources

The three algorithms are vendored as git submodules at the commits below.
These commits are the ones the measurements used; they are never bumped
silently, because MuseAir changed its algorithm between versions and a bump
would change every hash value and every timing.

| Hash | Repository | Branch | Commit | Language | License | Exported function |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| a5hash | `JoaoLopez/a5hash` | `main` | `7ff7fa34c406279f3f3203fb01d39c8b8cf263b1` | C, single header `a5hash.h` plus `a5hash_wrapper.c` | MIT | `a5hash_128_64(data, len, seed) -> uint64` |
| MeowHash 0.5 | `JoaoLopez/meow_hash` | `master` | `beeb71f01c2a3a85d5956589c0b14a825d28fdc9` | C++, `meow_hash_x64_aesni.h` plus `meow_wrapper.cpp` | zlib | `MeowHash_32(seed, len, data) -> uint32`, `GetMeowDefaultSeed()` |
| MuseAir BFast | `JoaoLopez/museair` | `oficial` | `91e7304675d35139e4be9054e793a5504393b2bd` | Rust crate 0.4.0, `museair_bfast_64` in `src/lib.rs` | MIT or Apache-2.0 | `museair_bfast_64(data, len, seed, out)` |

The wrappers in those forks are kept as they are: the package calls the same
exported functions, so the values are the same the `.so` files produce.

## Shape of the package

Repository `speedupy-native` in the organization's account, MIT for the glue
code, with a `NOTICE` file carrying the three upstream licenses.

```
speedupy-native/
├── Cargo.toml              # crate speedupy_native, cdylib, pyo3 + cc
├── pyproject.toml          # build-backend maturin; name speedupy-native
├── build.rs                # compiles the two C/C++ wrappers with the cc crate
├── src/lib.rs              # the PyO3 module: three functions and two flags
├── python/speedupy_native/__init__.py
├── vendor/a5hash/          # submodule, commit above
├── vendor/meow_hash/       # submodule, commit above
├── vendor/museair/         # submodule, commit above (path dependency in Cargo.toml)
├── tests/test_vectors.py   # known inputs and their hashes, one table per hash
├── NOTICE
└── .github/workflows/release.yml   # generated by `maturin generate-ci github`
```

One build system for the three: maturin builds the Rust crate, which depends
on the MuseAir crate by path and compiles `a5hash_wrapper.c` and
`meow_wrapper.cpp` in `build.rs`. The MeowHash wrapper is compiled only when
the target is x86_64, with `-maes -msse4.1` (`/arch:AVX` on MSVC); on any
other target the crate is built without it and the Python flag says so.

### Python API

```python
import speedupy_native

speedupy_native.a5hash_128_64(data: bytes, seed: int = 0) -> int   # 64-bit
speedupy_native.museair_bfast_64(data: bytes, seed: int = 0) -> int   # 64-bit
speedupy_native.meowhash_32(data: bytes) -> int   # 32-bit, MeowHash default seed
speedupy_native.HAS_MEOWHASH: bool   # False on arm64 and on x86_64 without AES-NI
speedupy_native.PLATFORM: str        # e.g. "linux-x86_64", for error messages
speedupy_native.__version__: str
```

`data` accepts anything with the buffer protocol. The seeds are the ones the
`.so` wrappers use today (`0` for a5hash and MuseAir, the MeowHash default
seed for MeowHash), so the results match the current libraries byte for byte.
Calling `meowhash_32` where `HAS_MEOWHASH` is false raises `RuntimeError`
with the platform in the message; `speedupy` turns that into the
`ImportError` its factory already raises for a missing driver.

### Platforms and wheels

| Wheel | a5hash | MuseAir | MeowHash |
| :--- | :--- | :--- | :--- |
| Linux x86_64 (manylinux) | yes | yes | yes |
| Linux aarch64 (manylinux) | yes | yes | no, `HAS_MEOWHASH` false |
| Windows x64 | yes | yes | yes |
| macOS x86_64 (Intel) | yes | yes | yes |
| macOS arm64 (Apple Silicon) | yes | yes | no, `HAS_MEOWHASH` false |
| sdist | builds anywhere with Rust and a C++ compiler | | |

MeowHash's official implementation exists for x86_64 with AES-NI only; the
project maintains no ARM port and says third-party ports are neither vetted
nor maintained. The package does not adopt one. The wheels use the stable ABI
(`abi3-py310`, matching D6), so there is one wheel per platform for every
Python from 3.10 on, and a new Python version needs no rebuild.

### Tests

`tests/test_vectors.py` holds, for each hash, a table of inputs (empty, one
byte, a short string, a 1 KiB block, a 1 MiB block, each as `bytes`) and the
expected values. The expected values are produced once with the current `.so`
files on Linux x86_64 and committed; from then on, every wheel the workflow
builds is installed and run against the same table on its own system, so a
value that differs between platforms fails the release. `speedupy`'s own
tests carry the same table (Task 25, step 1).

### Release

1. `maturin generate-ci github` writes the workflow: a matrix of builds on
   Linux, Windows and macOS runners (free in a public repository), one sdist,
   and a publish job that runs on a tag, with Trusted Publishing on PyPI (no
   token stored). The first release goes to TestPyPI.
2. Versions are SemVer tags without a `v`, as in `speedupy`. A change in any
   vendored commit is at least a minor bump and is written in the changelog
   with the old and new hash of one reference input.
3. `speedupy` pins `speedupy-native==X.Y.Z` in `pyproject.toml` and
   `requirements.txt`; a bump there is a pull request of its own, never a side
   effect.

## How `speedupy` uses it

Task 25 of the retrofit. `MeowHash.py`, `A5Hash.py` and
`MuseairBFastHash.py` call the three functions; `native.py`, the `.so`
loading, the `native` marker and `SPEEDUPY_REQUIRE_NATIVE` go away; the native
tests always run; a `native-platforms` CI job runs the hash tests on Windows
and macOS. Everything else in the suite keeps running on Linux only until the
whole suite is ported ("Out of the retrofit").

## Limits recorded with the decision

- MeowHash is unavailable on arm64 (see "Platforms"); the other five hashes
  work there. A paper that reports MeowHash numbers says they were measured
  on x86_64.
- MeowHash 0.5 was reclassified by its author after a published cryptanalysis:
  it is not for message authentication nor for hash tables exposed to
  collision attacks. A memoization cache in a non-adversarial setting is
  within its intended use; the documentation says so where the hash is
  offered.
- The pinned commits are frozen for the measurements. Upgrading MuseAir to the
  current crate (0.6, a different algorithm) is a new hash name, not a bump.
